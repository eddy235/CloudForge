# CloudForge — AWS-free deployment on Render

**No AWS account required.** This deployment path uses the same pinned,
fictional NexusDesk v1.0 demo that v0.1 and v0.2 tested. It adds a
self-contained Docker build and an optional Render Blueprint.

## What is demonstrated

1. **Cloud application delivery:** Docker-based web service, Render-managed
   HTTPS, health checks, build logs and deployment history.
2. **Infrastructure as Code:** versioned `render.yaml` defines source repo,
   branch, Dockerfile, environment, instance plan and health endpoint.
3. **Supply chain:** build fetches an exact NexusDesk commit; CI verifies
   the container runs under an unprivileged user and blocks operational routes.
4. **CI/CD:** GitHub Actions tests the Python/Terraform code, both Docker
   variants, and protected demo routes. The Render Blueprint specifies
   `autoDeployTrigger: checksPass` to gate deployments on CI.
5. **Security controls:** random `DJANGO_SECRET_KEY` generated by Render;
   synthetic demo mode; no private database, authentication, employee data or
   admin endpoints; CSP, HTTP-only/secure cookies and HTTPS at Render's edge.

This is **Render cloud engineering**, not experience administering or
deploying AWS App Runner, IAM, ECR or other AWS resources. The AWS Terraform
remains separately valid and non-deployed.

## Cost and hosting constraints

Render offers **Free** web service instances suitable for portfolios and
demos, subject to workspace-wide usage and service limitations.
Free services can spin down after 15 minutes without requests and require a
cold start on the next request. They use a temporary filesystem. Do not
assume free service hours are unlimited, especially if your other projects
also use Free instances in the same workspace.

Official information:
- https://render.com/docs/free
- https://render.com/docs/docker
- https://render.com/docs/infrastructure-as-code
- https://render.com/docs/deploys

**This release does not create any Render service.** Cloud deployment requires
a deliberate decision to use your existing Render workspace and its capacity.

## Source and Docker build

The original `Dockerfile` assumes a separately checked-out
`upstream/NexusDesk` directory, which is absent from GitHub because it is
ignored. Render must instead build **`Dockerfile.render`**, which retrieves
the exact NexusDesk SHA embedded in `UPSTREAM_VERSION`. The source-build
stage discards Git metadata before copying application files into the
non-root runtime stage.

To reproduce locally:

```bash
docker build -f Dockerfile.render -t cloudforge-render:test .
docker run --rm -d --name cloudforge-render-local \
  -p 127.0.0.1:8000:8000 \
  -e DJANGO_SECRET_KEY=local-dev-demo-secret-long-random-example \
  -e NEXUSDESK_DEMO_MODE=true -e DJANGO_DEBUG=false \
  -e DJANGO_ALLOWED_HOSTS=127.0.0.1,localhost \
  -e DJANGO_SECURE_SSL_REDIRECT=false -e DJANGO_ENABLE_HSTS=false \
  cloudforge-render:test
python scripts/smoke_local.py
docker rm -f cloudforge-render-local
```

## Optional Render deployment

The Blueprint is defined at the repository root in `render.yaml`:

- `name: cloudforge-demo` (a **new service**, not a replacement for the
  separately hosted NexusDesk demo)
- `plan: free`
- `runtime: docker`, Dockerfile path `./Dockerfile.render`
- Git source `eddy235/CloudForge`, branch `main`
- Git check-gated automatic deploys
- Health check `/health/`
- A generated random application secret and forced read-only demo flags

After approving the new Free service's shared-workspace usage, you may
create a **Render Blueprint** from
https://dashboard.render.com/blueprints and select `eddy235/CloudForge`.
Review every field and the plan before confirmation. Render will then
build and deploy the already-tested Dockerfile.

For a manual web-service setup choose Docker, `Dockerfile.render`, Free
plan, GitHub repo `eddy235/CloudForge` and branch `main`. Configure the
environment from `render.yaml` (generate a real secret rather than using
any literal example).

Never set `NEXUSDESK_DEMO_MODE=false` on the public CloudForge service.

## Verify the deployed service

When Render reports **Live**, run:

```bash
python scripts/smoke_cloud.py https://YOUR_CLOUDFORGE_RENDER_ORIGIN
```

It checks the fictional demo, static assets, restrictive CSP, blocked internal
routes, and rejected POST requests. The script requires an HTTPS origin.
Check the responsive layout and Render logs manually too. Do not invent a
CloudForge URL before an actual service exists.

## Rollback

Use the Render service's Deploys page to restore a previously verified
deployment. On Free instances, rollback history is limited. The service can
be suspended/deleted to stop using compute capacity; record its URL and
deployment status first. This does not affect your separately hosted
NexusDesk, SecureScan or portfolio sites.
